始终在线的智能体会无限期运行，自行决定在多个 session 中如何行动、何时行动。本文介绍它们的核心原语，以及这些原语如何组合在一起。

- 产品：Claude Platform
- 作者：William Hu
- 日期：2026 年 11 月 13 日
- 阅读时间：14 分钟

过去几个月，我们再次看到始终在线智能体升温。

始终在线智能体是有状态的、也会主动行动，也就是说它们会在多个 session 之间管理上下文，并在没有直接监督的情况下采取行动。在底层，它们运行的是与其他智能体相同的[核心循环](https://www.anthropic.com/research/building-effective-agents)。差别在于外围架构：这套架构由若干原语构成，用来控制智能体何时醒来、哪些信息会在各次运行之间保留，以及它们的工作成果如何送达用户。

这轮升温，很大程度上是因为近期的模型进步，让始终在线智能体变得更值得实际运行。首先，最新模型的判断力更好：它们更可靠地理解用户意图，也更清楚何时该向用户确认。其次，智能正在变便宜，长周期任务受益最大。例如，在[一项长周期编程基准](https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence)上，Opus 5.5 每个已解决任务的成本比 Opus 5 低 78%，而在典型工作负载上这一降幅是 40%。

客户已经开始询问，如何把这类体验接入自己的产品。有些公司希望让现有智能体更主动，有些则打算从零开始构建。

本文将拆解始终在线智能体背后的原语，并说明它们如何组合在一起。

## 始终在线智能体背后的循环

始终在线智能体其实并不是真正「始终开着」。这只是对用户体验的一种描述。

实际上，智能体大部分时间都在休眠，只是周期性地醒来做工作。每一段工作称为一次 **run**：智能体接收一个事件，完成任务，然后把发生过的事情保存下来。一次 run 在一个 **session** 里进行，session 是消息和工具调用的记录。run 结束后，智能体再次进入休眠，这个循环会无限重复下去。

![始终在线智能体时间线的动画示意图：大部分时间处于休眠、不消耗 token，中间穿插短暂的 run。每次 run 有四个步骤：事件到达、session 开始、智能体循环运行，以及这次 run 把状态写回存储，以便在各次 run 之间延续。](https://assets.claude.com/5dc803bf06d6e92e4aecae762da096626e2fa9ec.gif)

## 核心原语

始终在线智能体的外围架构有五个核心原语：事件收件箱、定时器、记忆、权限和发件箱。我们逐一看一下。

### 事件收件箱

大多数 AI 智能体只有在用户发来消息时才会运行。相比之下，始终在线智能体可以被多种事件触发，包括 webhook、定时任务和后台作业。

一种很诱人的做法是让每个事件源直接调用智能体，但这会带来几种失败模式。例如，两个事件同时到达可能启动相互竞争的 run，一次崩溃也可能把事件彻底丢掉。

这就是事件收件箱的用处。事件源不再直接调用智能体，而是把每个事件送到收件箱，再由 worker 取出处理。

最简单的版本有三个组件：

- 一份持久的事件列表，通常是一张数据库表；
- 一个 handler，通常是 HTTP 端点，负责把事件写入列表；以及
- 一个 worker，通常是后台服务，负责从列表中读取事件。

收件箱应跟踪每个事件的状态，并且可以依据来源提供的唯一标识做去重。关系型数据库很适合做收件箱，每个事件作为新行追加即可。我们建议先按每个用户一个收件箱起步，如果需要更高并行度，再继续拆分。

![事件收件箱示意图。handler（一个 HTTP 端点）把每个事件写入收件箱（一张跟踪状态并丢弃重复项的数据库表），并唤醒 worker。worker 读取待处理事件，启动 run，等待结束后将事件标记为完成。](https://assets.claude.com/bb08543a505cea3a24c88c718ceec4405e9c0a79.png)

新事件到来时，handler 把它写入收件箱并唤醒 worker。worker 读取所有待处理事件并启动一次 run。若事件是在延续先前的工作，例如用户的回复，就恢复已有 session；其余情况则开启新 session。

随后，worker 把事件交给智能体循环，等待这次 run 结束，再把对应事件标记为完成。实现细节可能相当棘手，下面是几条最佳实践：

- **handler 应尽快确认事件**。有些来源，例如 webhook 提供方，会把响应过慢视为失败。handler 仍可以做一些轻量检查，但任何更深入的校验，例如检查 prompt injection，都应放到 run 期间进行。
- **收件箱应作为唯一事实来源**。worker 被唤醒后，应先从收件箱拉取最新事件。这样，即使 worker 在 run 中途退出，新的 worker 也能捡起同一事件并重试。
- **一个收件箱同一时间只应有一个活跃 worker**。这样可以防止两次 run 重复劳动或互相覆盖。若 run 进行中又来了新事件，你可以把它推到下一次 run、并入当前 run，或者中断并重启。
- **worker 应把待处理事件批量合并**。例如，如果用户连续发送了好几条消息，worker 可以把它们合并进同一次 run，这样智能体只需回复一次。

### 定时器

定时器和事件收件箱一起，让始终在线智能体能够主动行动。定时器通常分为两类：跟进（follow-up）或日程（schedule）。跟进是智能体给自己设下的截止时间，例如稍后检查一则回复。日程则是按已知节奏重复发生的任务，例如每日通讯。

定时器存放在自己的持久存储中，通常是另一张数据库表，与收件箱分开。收件箱只应保存已经可以处理的事件。跟进和日程可以采用相似的 schema，但日程还需要跟踪其重复规则。

![定时器示意图。一次 run 在数据库表中设置定时器，要么是智能体设定的跟进，要么是用户设定的日程。调度器找出到期项，并向事件收件箱添加一个事件，从而启动下一次 run。](https://assets.claude.com/c16694e6d979a2ace84d03da0544297b7245c0a8.png)

定时器本身并不会发起 run。相反，一个调度器（通常是后台服务）按固定间隔轮询这张表，并触发所有已到期的项。每一轮中，调度器会：

1. 扫描存储，找出已到期的定时器。
2. 按类别更新每个定时器。
    1. 跟进应被标记为完成。
    2. 日程应把它的到期时间更新为下一次发生时间。
3. 向收件箱添加一个事件，并唤醒 worker。

调度器既可以自己实现服务，也可以使用持久执行引擎。

### 记忆

始终在线智能体要跨越许多互不连续的 run 工作，并依靠记忆来保持连续性。

与事件收件箱和定时器类似，记忆也应有自己的存储。在我们的产品中，例如 Claude Code 的 [auto memory](https://code.claude.com/docs/en/memory)，以及 Messages API 的 [memory tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)，这是用一个文件目录来实现的。对始终在线智能体来说，这些目录应映射到持久存储，通常是数据库或对象存储。这样，记忆就能比 worker 活得更久。

一条经验法则是：记忆只应保存智能体无法再次查到的内容。如果某样东西已经存在于另一个系统中，例如 issue tracker，你应保存一个指针，而不是再存一份。下面是始终在线智能体应保存的记忆类型：

- **用户指令：** 用户关于智能体行为的任何指令，都应保存在单独的文件中，并在每次 run 开始时加载。用户不会一直在场来引导智能体，所以这些指令必须在各次 run 之间延续。
- **用户笔记：** 智能体应保存它了解到的用户信息，例如用户的角色、偏好，或用户给出的任何纠正。可以先从单个文件开始，随着笔记增多再拆成若干小文件。在后一种情况下，每次 run 开始时只加载一份索引，但智能体可以在需要更多细节时，把单个文件拉进上下文。
- **过往消息：** 智能体应跟踪自己已经对用户说过什么，以免重复。它可以把这些内容存在单独文件中并在每次 run 开始时加载，也可以由 worker 加载智能体与用户最近的几条消息。
- **任务进度：** 对每个进行中的任务，智能体应保留一份进度文件，记录哪些已经完成、哪些还没做。之后的任何一次新 run 都可以读取该文件，并从上次停下的地方继续。与用户笔记类似，每次 run 开始时只加载一份索引，但智能体可以在需要更多细节时，把单个文件拉进上下文。

下图展示了一种示例布置。

![示例记忆布置示意图，表现为一个文件目录。instructions.md、index.md 和 reported.md 会在每次 run 开始时加载，而 notes/ 和 progress/ 文件夹则在需要时再读取。智能体在 run 期间写入记忆。](https://assets.claude.com/e5d209d7ef9b3455dec8a27b777dc12bdf806699.png)

以上都是在一次 run 期间保存的记忆。你还可以加入 dreaming：回顾过去的 session 来整理记忆。Dreaming 可以替换过时条目，并发现只有跨许多次 run 才会显现的模式。若想了解更多，我们关于[智能体记忆](https://www.anthropic.com/research/components-of-agent-memory)的文章有更详细的讨论。

#### 上下文窗口之内

在开始任何工作之前，智能体会加载系统提示、工具定义和记忆文件。这笔初始上下文「开销」会被计入每一次 run，所以我们建议保持精简，并使用[提示缓存](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)来降低成本。

新 session 开始时，只有这笔上下文开销，再加上触发这次 run 的事件。已有 session 则会带回它在先前各次 run 中的消息和工具调用。

如果一个 session 变得太长，你可以把较旧的消息[压缩（compact）](https://platform.claude.com/docs/en/build-with-claude/compaction)，或者开启一个新 session。这两种做法都会丢失细节，因此任何需要持久保留的内容，都应在过程中写入记忆。

![上下文用量随时间变化的动画图。系统提示、工具和记忆构成的固定带宽会出现在每一次 run 中。已有 session 会带回完整记录，并持续增长，直到压缩把较旧的记录变成摘要。](https://assets.claude.com/48757f0a147acfe841c943674c6214d34ed4405a.gif)

### 权限

权限是始终在线智能体风险最高的地方。一次 run 持有用户的访问权限，而且按设计是无人值守运行的。对于每一次工具调用，智能体都需要决定是自行继续、拦截，还是等待批准。

权限所用的组件，与其他智能体相同：

- **凭据存储：** 始终在线智能体往往需要用户的敏感凭据（例如密码或访问令牌）才能真正有用。[推荐模式](https://code.claude.com/docs/en/agent-sdk/secure-deployment#credential-management)是在智能体环境之外设置一个代理，由它把凭据加到出站请求上。智能体发出的请求不带凭据，代理在转发前再注入真正的凭据。
- **Auto mode：** 始终在线智能体应能在没有用户持续输入的情况下工作。我们已经在 Claude Code 的 [auto mode](https://www.anthropic.com/research/claude-code-auto-mode) 中处理过这类问题的一个版本。Auto mode 使用分类器审查风险较高的操作，并拦截它们识别为危险的操作，以便 Claude 寻找更安全的做法。不过，最重要的决策仍然需要用户审查。
- **延迟的工具调用：** 在 Claude Code 中，[hook 可以推迟一次工具调用](https://code.claude.com/docs/en/hooks#defer-a-tool-call-for-later)，并等待用户的额外输入。同一模式也适用于始终在线智能体，它们在采取某些行动之前可能需要澄清或批准。当一次调用被推迟时，这次 run 结束，session 会在调用中途被保存。请求会展示给用户（例如通过用 [MCP Apps](https://modelcontextprotocol.io/extensions/apps/overview) 构建的交互卡片），用户的答复再作为事件回到收件箱。该事件启动一次新的 run，用用户的输入恢复已保存的 session。在延迟调用等待响应期间，worker 可以处理其他事件，因此智能体不会被堵住。

### 发件箱

对大多数 AI 智能体来说，回复会在生成过程中流式传送给用户，因此用户可以跟着 Claude 一起看它如何推理问题、调用工具并写出答案。

始终在线智能体则不然，它们的大部分工作在后台完成。用户得到的是结果和少量细节，而不是完整的逐步拆解。

![发件箱示意图。一次 run 的结束方式可以是无话可说、一次 send 工具调用，或一次向用户提问的延迟工具调用。消息进入发件箱（一张数据库表），再由分发器送达用户。延迟请求可以走发件箱，也可以直接显示在你自己的界面中。](https://assets.claude.com/700b5f3a446f22493c0307ec65751b6b2f82ccb7.png)

一次 run 可以按以下三种方式结束：

- 智能体向发件箱发送一条消息，
- 智能体判断没有什么需要发送，或
- 智能体使用一次延迟的工具调用，请求权限或额外输入。

大多数始终在线智能体只需要一个「send」工具，直接把消息交给用户即可。只有在你希望控制智能体发消息的节奏，或希望智能体能从错误中恢复时，才需要正式的发件箱。

发件箱是一张单独的出站消息表，对应于事件收件箱。另外还有一个分发器，通常是后台服务，对应于 worker。分发器读取待发送消息，决定交付哪些，再把它们发给用户。来自延迟工具调用的请求，既可以走发件箱，也可以直接显示在界面中。

除了投递本身，还需要调节智能体发送消息的数量。发得太多会变得吵闹，发得不够又会漏掉用户需要知道的事情。我们建议构建 evals 来找到合适的平衡。实践中，更好的做法是让智能体先保持安静，再随着时间逐渐赢得更多用户注意力。

## 各部分如何组合在一起

五个原语是这样组合在一起的：

![五个原语如何组合的动画示意图。定时器和事件收件箱启动一次 run，这次 run 在 session 中结合记忆和权限开展工作，发件箱把消息交给用户，用户的答复再作为事件返回。](https://assets.claude.com/9f8df7b2dcc9d4637d27f37dae6e40a2a5851c8a.gif)

每一次 run 都从收件箱中的一个事件开始，无论它是用户消息、webhook，还是定时器。当 worker 取到一个事件，它就会启动一次 run，并在新的或已有的 session 中唤醒智能体。智能体读取记忆以获得基线，在权限范围内采取行动，再把学到的内容更新回记忆。run 结束后，智能体向发件箱写入一行，分发器再把消息交给用户。

它们共同构成一个循环。一次 run 可以设置一个定时器，稍后再次唤醒智能体；当用户回复一条消息时，答复会作为事件回到收件箱。每一次 run 都很短，但这个循环会无限持续下去，而这正是智能体让人觉得始终在线的原因。
